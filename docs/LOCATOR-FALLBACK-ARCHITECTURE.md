# Deterministic Tosca Locator Fallback Architecture — v52

## Why this layer exists

A Page Object still owns one readable primary locator. Tosca, however, frequently carries several pieces of technical identity for the same ModuleAttribute: HTML `id`, `name`, Duck Creek identity, `data-testid`, tag, label, class, source XPath, relative-ID context and source occurrence/index. Throwing those alternatives away makes a migration unnecessarily fragile.

v52 therefore preserves the alternatives in a sidecar catalog and uses them **only after the primary Page locator fails**.

## Runtime sequence

```text
Feature / Scenario / StepDefinition
        ↓
Page method
        ↓
Readable primary Page locator
        ↓
UiActions executes the requested action
        ↓ primary fails with locator/actionability error
DeterministicLocatorFallbackResolver
        ↓
Previously successful candidate for Page.Control/action (optional promotion)
        ↓
Ranked Tosca-derived candidate list
        ↓
Live probe of each candidate
  - must match exactly one element, unless Tosca explicitly supplied an occurrence/index
  - must be visible
  - must be enabled for an interactive action
  - must be editable for Fill
        ↓
Execute the **same failed action** on the candidate
        ↓
SUCCESS → log + HTML fallback trace + cache candidate + continue test
        ↓ all deterministic candidates fail
LLM/Copilot locator healing (if enabled)
        ↓
Final failure → AfterStep/AfterScenario evidence
```

Recovery deliberately lives inside `UiActions`, not `AfterStep`. ReqnRoll's `AfterStep` runs after the step has already failed and is therefore the right place for evidence, not transparent retry of a low-level page action.

## Source evidence

`Artifacts/ToscaLocatorPropertyCatalog.v52.json` combines the prior cross-application property catalog with the raw `38668CB4-6566-434E-90C3-2681457CA59BCL-EQ Total.tsu` export. The raw CL-EQ pass added 2,812 unique ModuleAttribute records.

The compiler can retain source-backed candidates from:

- `Id` / self-healing `attributes_id`
- Duck Creek ID / `data-duckcreekid`
- `Name`
- `data-testid`
- combinations of two or more technical attributes
- Tosca business type + accessible source text as Playwright role candidates
- label / associated-label evidence
- source tag + source text
- stable tag + exact class evidence
- exact source XPath (never synthesized)
- safe descendant `RelativeId` context
- literal Tosca `ConstraintIndex` occurrence only; buffer expressions are not guessed

## Candidate safety rules

The catalog may contain many candidates, but runtime does not click/fill the first thing that happens to exist.

1. Candidate confidence must meet `locatorFallback.minimumCandidateConfidence`.
2. Duplicate candidate signatures are removed.
3. Exact primary-equivalent candidates are removed unless the source adds meaningful specificity such as text, anchor or source occurrence.
4. A candidate that matches zero elements is skipped.
5. A non-source-indexed candidate that matches multiple elements is skipped.
6. Invisible/disabled candidates are skipped.
7. `FillAsync` refuses a non-editable control. A navigation DIV/heading cannot silently become a textbox action.
8. A candidate is considered recovered only after the originally requested operation itself succeeds.
9. If the recovered candidate fails on a later execution, fallback search resumes rather than permanently mutating Page Object source.
10. LLM/Copilot healing remains the final layer, after deterministic Tosca evidence is exhausted.

## Logging and HTML reporting

Every fallback event is written to the normal execution log. A successful recovery includes Page.Control, action, attempt number, strategy/value, Tosca source Module/field/property and confidence.

`ScenarioReport` also adds:

- a `Locator recovery` column beside each business step;
- a scenario-level `Locator fallback trace` table;
- every attempted candidate, match count, result and reason;
- the exact Tosca source file/Module/field/property used to derive it.

This report becomes normal per-test evidence and is attached to NUnit/Visual Studio/Azure DevOps by the existing test-evidence finalizer.

## Rebuilding catalogs

When a new Tosca export is received:

```powershell
python tools/extract_tosca_locator_catalog.py "C:\exports\CL-EQ Total.tsu"
python tools/build_locator_fallback_catalog.py
python tools/v52_fallback_gate.py
```

For Linux/macOS:

```bash
python3 tools/extract_tosca_locator_catalog.py "/exports/CL-EQ Total.tsu"
python3 tools/build_locator_fallback_catalog.py
python3 tools/v52_fallback_gate.py
```

Do not replace a human-validated primary locator merely because a generated fallback exists. The primary remains the clean Page Object contract; the sidecar catalog is resilient runtime evidence.
